# Finish the theme as a contract, not a palette

Mature design systems treat a theme as a full, finite contract. Every semantic token is defined in every mode, every declared foreground/background pair holds a stated contrast in every mode, and every mode is screenshotted. Color is only the first of roughly seven categories. The others are interaction states, elevation, typography, shape and density, motion and data-viz palettes. Most systems split their tokens into three tiers: raw primitives, then semantic roles that modes swap, then component tokens that alias the semantic tier and stay the same across modes. Modes are modeled as orthogonal axes (color scheme, contrast, color-vision deficiency, density) rather than as a growing list of hand-made themes. That approach is now standardized in the DTCG 2025.10 Resolver Module. Generation also follows a shared pattern. Material, Leonardo, Radix and Linear all pick colors by target lightness or target contrast in a perceptual space, and they treat "contrast" as a first-class input. QA rests on three automated gates and a set of known bug classes. The gates are a token-pair contrast matrix computed per theme, axe per rendered theme, and per-mode visual baselines. The bug classes are untokenized SVG, charts and code; box-shadow focus rings that vanish in forced colors; shadow-only elevation in dark mode; and a flash of the wrong theme. OMNI/UI-MAX's OKLCH engine already gets the hardest part right: it solves lightness to APCA targets per role and fails loudly. The work that remains is mostly structural. It needs a primitive tier and DTCG export; orthogonal mode axes with a continuous contrast parameter; generated (not hard-coded) state, elevation, motion and viz roles; reduced-motion and forced-colors output; and a QA loop that turns `omni specimen` from a gap-finder into a baseline-diffing gate. The specimen run itself shows that "APCA-validated" is not yet "QA'd": every light theme still produced two WCAG 2 failures, and every theme misused `text-3` for content that needs Lc 60.

## Three tiers and orthogonal axes are the settled architecture

The systems agree on structure more than their names suggest. Material 3 has reference tokens (`md.ref.palette.primary40`), system tokens (`md.sys.color.primary`) and component tokens (`md.comp.button.filled.container.color`). Dark mode, dynamic color and brand variants change only the system layer ([material-web theming](https://material-web.dev/theming/material-theming); [Design Systems Collective](https://www.designsystemscollective.com/the-token-structure-that-survives-five-products-google-uses-it-too-c480e864ef64)). Primer has **base** and **functional** tiers, plus "pattern" tokens such as `--button-primary-bgColor-rest` and `--control-checked-bgColor-hover` ([primer/primitives](https://raw.githubusercontent.com/primer/primitives/main/README.md); [Primer color](https://primer.style/foundations/primitives/color)). Carbon says outright that token **names never change across themes, only values** ([Carbon themes](https://carbondesignsystem.com/elements/themes/overview/)). Spectrum 2 maps one semantic token to different primitives per mode, so `--spectrum-background-base-color` points at gray-200 in light and gray-50 in dark ([@spectrum-css/tokens](https://unpkg.com/@spectrum-css/tokens@16.0.1/README.md)). Salesforce's SLDS 2 replaced its old design tokens with `--slds-g-` global hooks, including a numbered `surface-container-1..3` ladder paired with `on-surface-1..3` ([SLDS hooks](https://lightningdesignsystem.com/platforms/lightning/new-global-styling-hooks-guidance)). Names follow a `category-property-role-emphasis-state` grammar (`--p-color-bg-surface-hover`, `bgColor-accent-emphasis`, `color.background.brand.bold`), and the state is always the suffix ([Polaris tokens](https://cdn.jsdelivr.net/npm/@shopify/polaris-tokens@9.4.2/README.md)).

The size of a semantic layer is known in one case and estimated in another. **@material/web 2.4.1 ships 49 `md-sys-color` roles**, emitted as one token set with light and dark values ([_md-sys-color.scss](https://cdn.jsdelivr.net/npm/@material/web@2.4.1/tokens/_md-sys-color.scss)). Primer's visible light/dark set is about **236 color variables**: 92 foundational plus 144 pattern tokens, of which 68 are button, 38 control and 34 data-viz ([Primer primitives](https://primer.style/product/primitives/color/)). OMNI's current color contract has about 42 roles (8 surface and border, 3 text, focus, and 6 families of 5), which puts it in Material's range. It is missing two things that both Material and Primer have. One is a component/pattern tier. The other is a primitive tier underneath, so brand palettes can be swapped without re-solving roles.

Modes are where the systems scale. **Primer ships 9 color themes**: light and dark, each in default, high-contrast, colorblind (protan/deutan) and tritanopia versions, plus dark-dimmed. Each is an override file listing only the tokens that differ from its parent ([primer/primitives](https://raw.githubusercontent.com/primer/primitives/main/README.md)). Carbon ships 4 (White, G10, G90, G100) and lets any element become a theme zone ([Carbon themes](https://carbondesignsystem.com/elements/themes/overview/)). Spectrum's design data defines three independent **mode sets**: `colorScheme` {light, dark, wireframe}, `scale` {desktop, mobile} and `contrast` {regular, high}. Platforms can add or remove modes in each set ([Spectrum mode sets](https://opensource.adobe.com/spectrum-design-data/spec/mode-sets/)). Atlassian writes a space-separated multi-axis string such as `data-theme="light:light dark:dark spacing:spacing"` on `<html>`, with `contrastMode` as a separate option ([@atlaskit/tokens](https://cdn.jsdelivr.net/npm/@atlaskit/tokens@13.0.4/dist/types/set-global-theme.d.ts)). In Radix, appearance is independent of accent, gray, radius and scaling, and nested `<Theme>` elements override only the props they set ([Radix Theme](https://www.radix-ui.com/themes/docs/components/theme)). Material's Color Utilities treat contrast as a **continuous value from −1 to 1** rather than a flag ([MCU dynamic_scheme](https://cdn.jsdelivr.net/npm/@material/material-color-utilities@0.4.0/dynamiccolor/dynamic_scheme.d.ts)).

This structure is now standardized. DTCG reached its **first stable version, 2025.10, on 28 October 2025**. It is a Community Group report, not a W3C Standard ([W3C announcement](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). The Format Module defines `$value`, `$type`, aliases (`{colors.blue}`), `$extends`, `$deprecated` and reverse-domain `$extensions`. It also defines first-class types for every non-color category: dimension, fontFamily, fontWeight, duration, cubicBezier, shadow, border, transition and typography ([DTCG Format](https://www.designtokens.org/tr/2025.10/format/)). The **Resolver Module** models themes as always-on `sets`, `modifiers` with named `contexts`, and an ordered `resolutionOrder` in which later entries win. Its own example combines a theme modifier and a brand modifier for four resolutions, and it advises that each token be set by only one modifier ([DTCG Resolver](https://www.designtokens.org/tr/2025.10/resolver/)). Terrazzo 2.4 claims full 2025.10 support including resolvers ([Terrazzo changelog](https://unpkg.com/@terrazzo/cli@2.4.0/CHANGELOG.md)). Sources conflict on whether Style Dictionary v5 supports resolvers ([zeroheight](https://help.zeroheight.com/hc/en-us/articles/48049028236187); [DTCG list, Nov 2025](https://lists.w3.org/Archives/Public/public-design-tokens-log/2025Nov/0009.html)), so Terrazzo is currently the safer reference implementation.

Delivery is consistent across systems: custom properties scoped to a root selector, with subtree re-scoping. `light-dark()` has been Baseline since May 2024 but only switches when `color-scheme` includes both schemes ([MDN light-dark()](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark)). The `<meta name="color-scheme">` tag lets the browser paint the canvas correctly **before** the CSS arrives ([web.dev](https://web.dev/articles/color-scheme)). Flash prevention needs a blocking head script. Atlassian's own Bitbucket code sets `data-color-mode` by hand because "setGlobalTheme takes too long" ([Bitbucket theme.js](https://docs.atlassian.com/bitbucket-server/docs/9.0.0/reference/javascript/theme_theme.js.html)), and that script should be generated from the tokens so it cannot drift ([Josh Comeau](https://www.joshwcomeau.com/react/dark-mode/)). Material Web wraps every token in `var(--md-sys-color-x, <fallback>)` so components still render without a theme ([_md-sys-color.scss](https://cdn.jsdelivr.net/npm/@material/web@2.4.1/tokens/_md-sys-color.scss)). OMNI's boot script and its per-theme `color-scheme` already follow this practice. What OMNI lacks is the axis model: `data-theme` is a single flat name, so "studio, high contrast, compact, reduced motion" has to be authored as its own preset.

Four patterns in the table matter for a generator. First, **states are derived, not designed**. M3 computes them as one overlay rule applied to any role. Radix and Primer pre-bake them into named steps. A generator can do both: compute overlays, then optionally flatten them into opaque tokens for consumers that need solid values. Slack's dark-mode rebuild shows why the form matters. It had to store colors as RGB triplets so alpha could be applied at runtime ([Slack Engineering](https://slack.engineering/building-dark-mode-on-desktop/)), a problem that `color-mix()` now avoids.

Second, **elevation runs on two channels**, and in dark mode the surface ladder carries most of the meaning. Atlassian says "shadows are harder to see" in dark mode, so higher elevations get lighter surfaces while keeping their shadows ([Atlassian elevation](https://atlassian.design/foundations/elevation)). Material widens the gaps between surface tones as contrast rises. A shadow token that is not tied to a surface step is therefore only half a definition.

Third, **only a few non-color axes are switched by users**. Those are density/scale, radius and typeface; shadows, motion curves and spacing are usually fixed per brand ([Radix](https://www.radix-ui.com/themes/docs/components/theme); [Atlassian tokens](https://atlassian.design/foundations/tokens/design-tokens)). Motion is themable mainly through a reduced-motion context. Carbon and Fluent publish reduced-motion *guidance*, such as static alternatives and a no-motion setting ([Fluent motion](https://fluent2.microsoft.design/motion)), not a separate token set.

Fourth, **data-viz palettes have mode rules of their own**. Categorical colors need separate dark values. Sequential ramps flip so that "more" is always the higher-contrast end. Diverging ramps can stay the same in both modes ([Carbon data-viz](https://carbondesignsystem.com/data-visualization/color-palettes/)). Since common categorical sets stop at 8–10 colors, more than about 10 series is a cue to group data rather than add hues.

Some values in this area are unverified. The 38% disabled-content and 12% disabled-container opacities are widely reproduced from M3 component tokens, but no primary file was fetched. M3's density steps and Carbon's component heights were not confirmed either. Okabe-Ito hex values were not checked against a primary source, so verify them before shipping a CVD-safe palette.

## Generators solve to contrast per role, and contrast is an input

All four reference generators work in a perceptual-lightness space and place colors by target, not by mixing. Material Color Utilities builds 0–100 tonal palettes in HCT. It assigns roles to tones (light primary 40, dark primary 80, containers 90/30) and enforces a **contrast curve per role** at low, standard, medium and high contrast: text on surface at 4.5/7/11/21, primary at 3/4.5/7/7, outline at 1.5/3/4.5/7, containers at 1/1/3/4.5 ([MCU color_spec_2021](https://raw.githubusercontent.com/material-foundation/material-color-utilities/main/typescript/dynamiccolor/color_spec_2021.ts)). It ships 10 scheme variants, from MONOCHROME to FRUIT_SALAD ([MCU variant.ts](https://raw.githubusercontent.com/material-foundation/material-color-utilities/main/typescript/dynamiccolor/variant.ts)). Radix hand-tunes 12 steps but guarantees **APCA Lc 60 for step 11 and Lc 90 for step 12** on step 2 ([Radix scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)). Leonardo solves directly. It interpolates key colors and searches for target ratios against one background, with a global `contrast` multiplier and `lightness` and `saturation` controls ([Leonardo](https://raw.githubusercontent.com/adobe/leonardo/main/packages/contrast-colors/README.md)). Linear reduced **98 hand-set variables per theme to 3 LCH inputs**: base, accent and contrast. The contrast input also drives its high-contrast themes ([Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)).

OMNI's engine already belongs to this family. It takes a few OKLCH inputs, solves lightness against the hardest surface each role sits on, and reports every pair. Compared with MCU, though, three things are missing. The first is a **contrast curve that covers non-text roles**. MCU raises outline contrast from 3 to 7 and container separation from 1 to 4.5 as contrast increases, so in high contrast the borders and surface steps get stronger, not just the text. OMNI's `contrast: 'high'` shifts surfaces by a fixed 0.04 L and raises text targets, but border lightness is hard-coded per mode. The second is **continuity**. A −1…1 contrast value would let one preset produce standard, medium and high variants, plus a "dimmed" dark like Primer's, without new preset files. The third is **dual gating**. The specimen run showed every light theme passing its APCA-solved roles while axe flagged two WCAG 2 failures (3.6:1 and 4.3:1) per light theme. Primer gates on WCAG 2 ratios because they are still the compliance bar, and treats APCA as the perceptual target ([GitHub Blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)). A theme engine should solve to APCA and also verify WCAG 2. The current working copy has started doing this for placeholder text, viz marks and lit legends, and the same rule should apply to every text pair.

The specimen's APCA failures point to a missing role, not to a solver bug. All seven themes failed on the same two elements. One is `text-3` sample text ("Placeholder and disabled only") at Lc 52–54 in dark themes. The other is code comments colored with `text-3` at Lc 53–58. `text-3` is solved for Lc 45–50 because it is meant for placeholder and disabled text, and the specimen's own probe demands Lc 60 for readable content. A code comment is content. The fix is to add a `syntax-*` family (comment, keyword, string, number), solved to Lc 60 and paired light/dark, which is what practitioners recommend for code highlighting ([Codercops](https://blog.codercops.com/blog/dark-mode-implementation-guide-2026)). Separately, the specimen's probe should apply the 45 threshold to elements it knows are placeholder or disabled. Primer's lesson applies here: shared colors couple pairs, so a fix to one role can break another, which is why the **whole pair table is rechecked on every change** ([GitHub Blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)).

## Theme QA is a pair matrix, per-mode baselines and a known bug list

The reference QA approach comes from Primer. The team declared **100+ foreground/background pairs, each with its required ratio**. A script computes every pair in every theme, flattening translucent tokens against the page background first, and prints ratio, minimum and pass/fail in seconds. It runs as a GitHub Action on every PR, and it surfaced hundreds of contrast issues across more than 1,000 use cases ([GitHub Blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)). `validate()` in OMNI is this pattern already, minus three things: CI wiring, alpha flattening for the new `color-mix()` state roles, and pairs for borders, focus and state-on-surface.

Rendered checks come next. axe's `color-contrast` rule checks text at WCAG AA. It cannot see text over background images or gradients, and it returns hard cases as "incomplete" ([Deque](https://dequeuniversity.com/rules/axe/4.10/color-contrast)), which is where theme bugs hide. Storybook's a11y addon gates CI only when `parameters.a11y.test` is `'error'` and documents no per-theme runs ([Storybook a11y](https://storybook.js.org/docs/writing-tests/accessibility-testing)), so running it per theme is up to the team. Playwright can emulate every relevant preference: `colorScheme`, `reducedMotion`, `forcedColors` and `contrast: 'more'` ([Playwright emulation](https://playwright.dev/docs/emulation)). Its `toHaveScreenshot` already disables animations and hides the caret by default. Project names go into baseline filenames, so one project per theme gives each theme its own baseline. Baselines must be generated in the same OS image they are compared in ([Playwright snapshots](https://playwright.dev/docs/test-snapshots)). Chromatic modes do the same for stories. Baselines are keyed by **mode name**, and cost is stories × modes ([Chromatic modes](https://www.chromatic.com/docs/modes/)). For hosted options, Lost Pixel was **sunset in April 2026**. Argos is free up to 5,000 screenshots a month (per its own comparison, which is a competitor's claim) ([Argos](https://argos-ci.com/blog/lost-pixel-alternatives)). For a CLI toolkit that already drives Playwright, self-hosted baselines are the natural fit.

Linting closes the loop on what a theme cannot reach. `stylelint-declaration-strict-value` with a `/color$/` regex rejects raw hex ([README](https://unpkg.com/stylelint-declaration-strict-value@1.11.1/README.md)). Mozilla enforces token families per property ([use-design-tokens](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens/color.html)). Atlassian migrates in two lint stages: `ensure-design-token-usage`, then `no-unsafe-design-token-usage` with fallbacks banned ([Atlassian ESLint](https://atlassian.design/components/eslint-plugin-design-system/no-unsafe-design-token-usage)). Without lint, apps end up in "an incomplete mix of light and dark themes," which is what Atlassian's unmigrated apps showed after tokens 1.0 ([Atlassian community](https://community.developer.atlassian.com/t/upcoming-changes-in-design-tokens-1-0-0-action-required-soon-edit-now-live/66243)).

The recurring bug classes are well documented. Focus disappears in Windows High Contrast when CSS sets `outline: none` ([Mozilla bug 1893730](https://bugzilla.mozilla.org/show_bug.cgi?id=1893730)). Box-shadow focus rings lose their color in forced colors ([Tempertemper](https://www.tempertemper.net/blog/windows-high-contrast-mode-and-focus-outlines)). Components need `border: … solid transparent` so their shapes survive when backgrounds are stripped ([WWU guide](https://marcom.wwu.edu/accessibility/guide/support-forced-colors)). These bugs appear only on Windows or under `forcedColors: 'active'` emulation. Default UA colors fail as well: WebKit's link blue is **2.23:1 on black** when `color-scheme` is missing ([web.dev](https://web.dev/articles/color-scheme)). Practitioner reports converge on further problems: shadows vanish on dark surfaces, logos and inline SVG lose their edges unless they use `currentColor`, chart axes and status colors fail on dark, light syntax themes become unreadable, and third-party widgets fall out of sync ([Bellog](https://bellog.vercel.app/en/posts/dark-mode-implementation-traps); [Codercops](https://blog.codercops.com/blog/dark-mode-implementation-guide-2026)). Rollout follows a consistent sequence: feature flag, then staff dogfooding for weeks, then a public preview, then GA. The GA switcher offers a single theme or "sync with system" with separate day and night themes ([GitHub Blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/); [GitHub Docs](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-personal-account-settings/managing-your-theme-settings)).

## What OMNI/UI-MAX should build to finish the theme system

The current working copy of `src/theme-engine.js` has begun emitting first-pass values for all 21 roles. State layers are `color-mix()` overlays of `text-1` at 8/10/12/16%, with selected at 18% of `accent-solid` and disabled opacity at 0.38. There are three fixed shadow stacks per mode, shape scales chosen by a `shape` keyword (sharp/soft/round), font stacks from the preset, `calm`/`snappy` motion, and 8 viz hues solved to 3:1 on panels. That is the right shape. Measured against the research, the next steps fall into five groups.

**Make the axes orthogonal and contrast continuous.** Split the single `data-theme` into independent axes in the Atlassian/Spectrum style: `data-theme` (concept and scheme), `data-contrast` (standard, more, or a numeric level), `data-cvd` (none, protan-deutan, tritan), `data-density` (a Radix-style 90–110% `--scaling` applied to space, size and type) and `data-motion` (full, reduced). Store CVD and contrast variants as Primer-style delta overrides on a base theme, not as new presets. Then `flight-deck-hc` becomes `flight-deck-night` + `contrast: more`. Replace `contrast: 'normal'|'high'` with an MCU-style −1…1 value that feeds a per-role contrast curve, so outlines, `border-*` and surface-ladder gaps scale along with text. Extend the boot script's precedence chain to set each axis, including `prefers-reduced-motion`. Each resolved combination should be one Resolver `contexts` entry when exported.

**Add a primitive tier and DTCG I/O.** Generate per-hue OKLCH ramps as `ref.*` primitives and alias roles to them. This lets a brand swap its palette without re-solving every role, and lets `themegen` emit `.tokens.json` plus a `.resolver.json` (version `2025.10`), with OMNI metadata such as the APCA targets and concept under `$extensions` keyed `dev.omni.*`. Terrazzo can then build platform outputs. Keep the CSS output, and wrap the theme block in `@layer tokens` so app styles win without specificity fights. That is a standard-practice inference rather than a cited system rule.

**Derive the non-color roles from the color solution instead of hard-coding them.** The five role groups need different changes.

| Role group | Current working copy | Change suggested by the research |
|---|---|---|
| `state-*` | Overlays of `text-1`; pressed 12%, selected 18% accent | Overlay each family's *own* on-color (M3 rule), not always `text-1`. Emit flattened opaque twins (`*-hover-solid`) and add state-on-surface pairs to `validate()` with alpha flattened. Keep pressed at 12% as a deliberate choice: Flutter's latest is 10%, but 12% separates more clearly from hover |
| `shadow-1..3` | Fixed rgba stacks per mode | Pair each with `surface-1..3` as one elevation token. In dark mode, add a light hairline border per level, and scale ladder gaps with contrast (MCU widens dark containers 22→30 at high). Add `scrim` and a z-index ladder (Atlassian 100–800) |
| `radius-*` | 3 keyword scales + full | Derive from one `radius` factor (Radix), so `full` makes controls pills; keep M3's 4/8/12/16/28 as the "soft" reference |
| `font-*`, type | Two family stacks | Add brand/plain/mono family roles (M3) and a 12–15 role type scale with size, line-height, weight and tracking (negative at display, positive at small labels; 4px line-height grid), scaled by density |
| `duration-*`, `ease-*` | calm/snappy, 3 durations, 3 easings | Map onto Carbon's productive/expressive split; emit a `@media (prefers-reduced-motion: reduce)` block that collapses durations or changes spatial moves to fades (the code comment promises this but `toCSS` doesn't emit it yet) |
| `viz-*` | 8 fixed hues at C 0.13, 3:1 vs `surface-1` | Generate in OKLCH at near-equal L with a fixed order, then check minimum pairwise ΔE under simulated protan, deutan and tritan vision. Add sequential ramps (reversed in dark) and diverging ramps (unchanged), a `viz-other` neutral, and chart axis/grid roles |

**Add the roles the specimen does not yet ask for.** These are `syntax-*` (which fixes the shared APCA failure), `scrim`/`overlay-backdrop`, `selection-bg`, `link`/`link-visited`, `skeleton`, `caret`/`accent-color` for native controls, and focus-ring width/offset (commonly 2px/2px, held to ≥3:1 non-text contrast). Expand the forced-colors block beyond `--focus: Highlight`: map surfaces to `Canvas`, text to `CanvasText`, borders and focus to system colors, and require transparent borders on controls. Then add the new roles to `REQUIRED_ROLES` so the specimen keeps acting as the completeness check.

**Turn the specimen into a gate.** `omni specimen` already renders one component × state sheet per theme, colors gaps with hazard stripes, and runs APCA plus axe. That is the "all-states grid" pattern that keeps snapshot cost at one image per mode. To make it a gate, run the sheet as Playwright projects per axis combination (scheme × contrast × forced-colors × reduced-motion), awaiting `document.fonts.ready` before each capture. Commit baselines generated in a pinned image and diff them with the existing `src/diff.js`. Fail on any `validate()` miss, any WCAG 2 text failure, any missing role, and any theme whose role key set differs from the others. Add CVD-simulated captures for the status and viz rows, the place where "red text alone" and look-alike series hues fail. Run the full matrix on main or nightly and only default light and dark on PRs. Finally, extend `omni check`'s raw-color count to SVG `fill`/`stroke`, chart configs and inline styles, the places where untokenized color survives. The skill text should stop saying "ship dark, light and high-contrast". It should instead define done as: every role present in every mode, the pair table green, specimen baselines approved by a human, and the switcher offering System/Light/Dark with separate day and night picks.

## Conclusion

The research reframes "complete theme" from a number of roles to a set of closed loops. A role is finished only when it has a generation rule tied to the color solution, a declared pair with a target in every mode, and a rendered baseline someone has approved. By that standard OMNI's color layer is close to finished, and its new non-color roles are placeholders that still need generation rules. The specimen is the right instrument, and its first real finding (`text-3` doing a content job) was a missing role, the kind of gap only a rendered matrix shows.

The bigger design choice is to adopt axes before adding presets. Every system that scaled past four themes (Primer's 9, Spectrum's mode sets, Atlassian's multi-axis string) did it with delta overrides on orthogonal axes, and DTCG has now standardized that model. A continuous contrast parameter and a CVD axis would turn OMNI's seven hand-tuned presets into a generated matrix, and the specimen gate would then decide which cells of that matrix ship. Two cautions remain. APCA thresholds are the better perceptual target but not the compliance bar, so dual gating is necessary. And several reference numbers in this area (M3 disabled opacities, density steps, CVD palette values) still need primary-source verification before they become defaults.
